# Spyder Wallet — Block 7, Stage 2: Локальная подготовка подписи EIP-1559

## Установка

`console-update-spyder-wallet-block7-stage2-cumulative-20261101.zip` — **накопительный патч только для Block 7**. Он включает всё из Block 7 Stage 1 и Stage 2. База: `kepler-spider-main 3.zip` + `console-update-spyder-wallet-terminal-unified-rechecked-20261101.zip` или уже установленный Block 7 Stage 1. Никаких изменений Chat, Terminal, push, WalletVault или серверных файлов.

**Это НЕ разрешение на использование реальных средств.** Подпись подготовлена как изолированный локальный примитив для будущего контролируемого использования. Кнопка отправки на экране остаётся заблокированной, `eth_sendRawTransaction` отсутствует. В коде нет публикации подписанного payload, сохранения подписанных байтов или криптоключей на сервер.

## Реализация

- Неизменяемая модель неподписанной транзакции с проверками: возраст quote < 45 секунд (с запретом дат из будущего), совпадение выбранного кошелька, сеть Ethereum Mainnet/chainId 1, адрес отправителя/получателя, ненулевые суммы, пределы nonce/gas/fee.
- Точное кодирование количества ETH (18 знаков), USDT/USDC (6 знаков), безопасное big-endian кодирование gas, nonce и EIP-1559 комиссий. Контракты USDT/USDC закреплены в Stage 1.
- Изолированный `WalletEVMOfflineSigner` использует существующую Trust Wallet Core 4.2.9 (`HDWallet`, `EthereumSigningInput`, `AnySigner`); исходный seed запрашивается из защищённого Keychain при использовании подписывающего метода. Выполняется сравнение выведенного Ethereum-адреса с адресом из проверенного quote.
- Отказ при устаревшей котировке, неверном выбранном кошельке, неверном выходном формате EIP-1559 или несовпадении закодированного ERC-20 calldata.
- Для iOS XCTest добавлен эталонный Wallet Core тест EIP-1559 / ERC-20 с **публичным тестовым приватным ключом**, только для автоматических тестов, не из пользовательского vault. Данные совпадают с опубликованным в официальном репозитории Trust Wallet Core примером.

## Почему отправка недоступна

Это следующий инженерный шаг, но не завершённый Transaction Engine. Ещё необходимы: полноценный `xcodebuild build` и `xcodebuild test` на macOS; верификация протокола и подписи на реальном iPhone; независимая проверка криптографического и memory-lifetime кода; транзакционный confirm UI; nonce reservation, повторная проверка gas перед отправкой; корректное поведение при reorg/replacement, проверка receipt и статусов; обработка неоднозначного ответа RPC без риска дублирования; EIP-55; тесты на testnet (Sepolia) до включения mainnet. Swift `String`/`Data` не гарантируют полного уничтожения секретов в оперативной памяти — отдельный hardening обязателен.

В частности, в Stage 2 намеренно **не реализована** сеть для публикации транзакций, не включена кнопка подписи в Send Flow и не изменены existing Core Vault APIs.

## Две проверки перед передачей

1. На рабочем исходном дереве: исходники, сигнатуры Swift API (в Linux адаптер проверяется только против проверенной формы API, **не** против реального iOS WalletCore binary), декодирование и кодирование, циферные кейсы, все Python/TerminalKit/Node тесты, Swift parse.
2. После упаковки: ZIP распаковать заново в чистую копию базового репозитория поверх предыдущих архивов, сверить контрольные суммы затронутых файлов, повторить все проверки и XcodeGen YAML parsing.

**Не заявлять успешный TestFlight без фактической macOS Xcode сборки.**
